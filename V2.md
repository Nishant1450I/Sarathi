# SARATHI Skill Assessment V2.1: Improvements, PRD and Build Prompt

This document builds on the current Skill Assessment V2 structure (mode select, consent, active engine, server grading, results). It has three parts: suggested modifications, a PRD for the first release of them, and a ready-to-paste prompt for a coding agent.

## Part 1: Suggested Modifications

### A. Security and code execution (highest priority)

1. **Sandbox the runner.** `localDevDriver.js` runs candidate code in Node child processes with only a 2000 ms timeout. Untrusted code needs isolation: run it in a container or microVM (Docker with gVisor, `isolated-vm`, or a hosted runner such as Judge0), with no network, a read-only filesystem, and CPU and memory limits.
2. **Harden SQL.** Besides read-only SQLite, allow only a single `SELECT`/`WITH` statement, reject `PRAGMA`, `ATTACH` and multiple statements, and enforce a row cap and a query timeout.
3. **More languages.** Add Python first (needed for Data Science and AI/ML), then Java, behind a common `RunnerDriver` interface so `gradingService` does not change.
4. **Hidden-test integrity.** Never send hidden test inputs or expected outputs to the client. Return only pass/fail counts and a category label for hidden tests.

### B. Fairness and integrity

5. **Integrity score with tiers.** Keep the non-accusatory approach, but aggregate events (tab switches, blur, paste, offline) into a Low / Medium / High review-priority flag for reviewers. It never changes the candidate's score automatically.
6. **Paste context.** Distinguish paste inside the editor from paste elsewhere, and log paste size, so reviewers can tell a small snippet from a full solution.
7. **Code similarity check.** After submission, compare solutions between candidates for the same question using normalized tokens or AST fingerprints, and surface high matches to reviewers.
8. **Candidate appeal flow.** Let candidates add a short note on flagged events (for example, "my internet dropped"), shown next to the flags in the reviewer queue.
9. **Server-authoritative timer.** The client countdown is only a display. The server stores the start time and deadline, rejects late submissions, and returns the remaining time on resume.

### C. Question selection and scoring

10. **Randomized pools.** Each question slot draws from a pool of equivalent items, so two candidates rarely see the same set. Add exposure counters so no item is overused.
11. **Adaptive difficulty (light).** Start at difficulty 2. Move up after correct answers and down after incorrect ones, within the mode's time budget. This gives better level resolution with fewer questions.
12. **Partial credit for code.** Score by the fraction of tests passed (visible plus hidden), weighted so hidden tests count more, instead of all-or-nothing.
13. **Configurable weights.** Move the 40% Knowledge / 60% Practical split and the evidence-cap rules into a per-domain config file, so Cybersecurity can weigh knowledge higher than Web Development.
14. **Explanation scoring.** For MCQs with an explanation field, run an optional rubric-based check and flag only low-confidence cases for a human, never auto-penalize.
15. **Project grading.** For `project` items, use a rubric with weighted criteria, an optional automated repo check (README present, tests present, build passes), and reviewer sign-off before it affects the level.

### D. Candidate experience

16. **Resume anywhere.** On refresh or crash, restore answers, code, current question and remaining time from the server (autosave already exists; add conflict handling: the newest `updatedAt` wins, with a version counter).
17. **Offline-tolerant autosave.** Queue failed saves and retry with backoff, with a visible "Saved / Saving / Offline" indicator.
18. **Better accommodations.** Extend beyond 1.5x time: 2x option, extra breaks, high-contrast and larger-text modes, full keyboard navigation, and screen-reader labels on the palette and editor. Target WCAG 2.1 AA.
19. **Pre-flight check.** Before starting, check browser support, camera permission (only for Secure mode), network quality and editor loading, with plain-language fixes.
20. **Practice mode feedback.** Show explanations after each answer in Practice mode, and keep Secure mode explanations until the results page.

### E. Results and downstream value

21. **Skill radar and sub-skills.** Tag each question with sub-skills (for example, for Web Development: HTML/CSS, JavaScript, React, APIs) and show a radar chart on `ResultsReport.tsx`.
22. **Percentile and history.** Show the candidate's percentile within the domain and a trend across attempts.
23. **Retake policy.** Cooldown (for example, 7 days) for Secure mode, unlimited Practice, and a different question pool on retake.
24. **Verified skill badge.** A shareable, expiring credential (for example, 12 months) with a public verification URL, showing the level and tier, and no personal answers.
25. **Smarter gap plan.** Make `SkillGapPlan.tsx` map each weak sub-skill to specific resources or SARATHI courses, and offer a "re-test this sub-skill only" short assessment.

### F. Reviewer and admin tools

26. **Reviewer queue upgrades.** Filters (domain, integrity tier, status), SLA timers, side-by-side answer and event timeline, and an audit log of every reviewer decision.
27. **Question authoring UI.** A recruiter/admin screen to create, preview and version questions, with schema validation, instead of hand-editing the JSON seeds.
28. **Item analytics.** Per-question pass rate, average time and discrimination index, to find broken or too-easy items.
29. **Seed validation in CI.** A script that validates every seed file (unique IDs, valid `type`, `difficulty` 1 to 3, at least N hidden tests for code questions) and fails the build on errors.

### G. Privacy, compliance and engineering hygiene

30. **Data retention and consent.** State what is stored (events, code, scores), set retention periods, and give candidates a data-deletion path. This should align with India's DPDP Act 2023 obligations (consent, purpose limitation, erasure). Confirm details with legal counsel.
31. **Camera stays local.** Keep the current local-only preview and state this clearly on the consent screen.
32. **Staged rollout.** Replace the on/off flags with a percentage rollout (`ASSESSMENT_V2_ROLLOUT_PCT`) plus per-feature flags for adaptive difficulty, similarity checks and badges.
33. **Tests and telemetry.** Unit tests for grading and evidence caps, end-to-end tests for the full lifecycle, and metrics for completion rate, drop-off by step, runner errors and save failures.
34. **Keep the 200-line rule.** Add an ESLint `max-lines` rule so the modular structure does not erode.

### Suggested phasing

| Phase | Focus | Items |
| --- | --- | --- |
| 1 (P0) | Safety and trust | 1, 2, 4, 9, 16, 17, 29, 33 |
| 2 (P1) | Fairness and scoring quality | 5, 6, 8, 10, 12, 13, 18, 26 |
| 3 (P1) | Candidate value | 3, 19, 21, 22, 23, 25 |
| 4 (P2) | Scale and ecosystem | 7, 11, 14, 15, 24, 27, 28, 30, 32 |

## Part 2: Product Requirements Document (PRD)

**Product:** SARATHI Skill Assessment V2.1 **Release scope:** Phase 1 and Phase 2 above **Status:** Draft for review

### 1. Background and problem

V2 introduced a modular assessment with Practice and Secure modes, server-side grading, evidence caps and a reviewer queue. Gaps remain: candidate code runs with minimal isolation, the timer and resume behavior depend too much on the client, scoring is all-or-nothing for code, integrity signals are raw events rather than a usable review signal, and accessibility support is limited to a time multiplier.

### 2. Goals

- G1: Make code execution safe for untrusted input.
- G2: Make assessments resilient to refresh, crash and flaky networks.
- G3: Make scores more accurate and fair (partial credit, configurable weights, randomized pools).
- G4: Give reviewers a prioritized, explainable integrity view without automatic penalties.
- G5: Improve accessibility to WCAG 2.1 AA for the candidate flow.

### 3. Non-goals

- Automated disqualification based on integrity events.
- Video or audio recording or upload of the webcam feed.
- Full adaptive testing (IRT calibration), which is deferred to Phase 4.
- Verified badges and public credentials, which are deferred to Phase 4.

### 4. Users

| User | Need |
| --- | --- |
| Candidate (student) | Fair, stable test; clear feedback; accommodations when needed |
| Reviewer / recruiter | Fast triage; evidence for decisions; audit trail |
| Admin / content owner | Safe, validated question content |
| Developer | Modular code, tests, safe rollout |

### 5. Functional requirements

**Runner and execution**

- FR-1 (P0): All candidate code runs in an isolated sandbox with no network access, a 128 MB memory limit (configurable), a CPU time limit, and an output size limit.
- FR-2 (P0): `RunnerDriver` exposes a single interface `run({language, code, tests, limits})` returning `{passed, failed, stdout, stderr, timedOut}`. Drivers: JavaScript (sandboxed), SQL, and Python.
- FR-3 (P0): SQL runner accepts exactly one `SELECT` or `WITH ... SELECT` statement; rejects `PRAGMA`, `ATTACH`, DDL and DML; enforces a 1000-row cap and timeout.
- FR-4 (P0): Hidden test inputs and expected outputs are never included in any client response. The client receives only aggregate counts for hidden tests.

**Session, timer and resume**

- FR-5 (P0): The server records `startedAt` and `deadlineAt` per attempt (including accommodation multiplier). Submissions after `deadlineAt` plus a 10-second grace are rejected, and the last autosaved answers are graded instead.
- FR-6 (P0): `GET /attempts/:id/state` returns answers, code, current question index, and remaining seconds, so the client can restore after refresh.
- FR-7 (P0): Autosave sends a `version` counter. The server rejects older versions with a conflict response, and the client re-syncs.
- FR-8 (P0): Failed saves are queued in `sessionStorage` and retried with exponential backoff. The UI shows Saved, Saving or Offline.
- FR-9 (P0): Final submission is idempotent: repeating it returns the same result.

**Scoring**

- FR-10 (P1): Code questions award partial credit as `weightedPassRate = (visiblePassed*1 + hiddenPassed*2) / (visibleTotal*1 + hiddenTotal*2)` times the difficulty points.
- FR-11 (P1): Scoring weights (Knowledge vs Practical) and evidence-cap thresholds load from `server/src/config/assessmentScoring.json` per domain, with the current 40/60 split and caps as defaults.
- FR-12 (P1): Each attempt draws questions from pools. A pool is a set of items with the same `slot`, `type` and `difficulty`. Selection avoids items the candidate saw in a previous attempt where possible.

**Integrity and review**

- FR-13 (P1): `integrityService` computes a review-priority tier (Low, Medium, High) from event counts and durations using thresholds in config. The tier is shown only to reviewers.
- FR-14 (P1): The paste event records whether it happened inside the editor and the number of characters pasted.
- FR-15 (P1): After the attempt, the candidate may add one note of up to 500 characters about flagged events. The note appears in the reviewer queue.
- FR-16 (P1): The reviewer queue supports filters (domain, tier, status), sorting by submission time, and an audit log entry for every decision (who, when, what changed).

**Accessibility**

- FR-17 (P1): `RulesConsent.tsx` offers time multipliers of 1.0x, 1.5x and 2.0x, and toggles for high contrast and larger text. Choices are stored on the attempt.
- FR-18 (P1): All interactive elements in the candidate flow are keyboard-operable with visible focus, and the question palette and editor have ARIA labels and live-region announcements for timer warnings.

**Quality tooling**

- FR-19 (P0): `npm run validate:seeds` checks all seed files for unique IDs, valid fields, and at least 2 hidden tests per code question, and runs in CI.
- FR-20 (P0): ESLint `max-lines` of 200 is enforced for `src/components/assessment/`.

### 6. Non-functional requirements

- **Security:** No candidate code runs in the API server process. Sandboxes are destroyed after each run.
- **Performance:** The median code run returns within 3 seconds. p95 under 8 seconds. Autosave p95 under 500 ms.
- **Reliability:** No answer loss when the browser refreshes or the network drops for up to 5 minutes.
- **Privacy:** Webcam frames never leave the device. Retention periods are documented and configurable.
- **Compatibility:** Latest two versions of Chrome, Edge, Firefox and Safari.

### 7. Data model changes

| Entity | New or changed fields |
| --- | --- |
| `attempt` | `startedAt`, `deadlineAt`, `timeMultiplier`, `a11yPrefs`, `saveVersion`, `submittedAt`, `poolSelection` |
| `answer` | `questionId`, `value`, `updatedAt`, `version` |
| `integrityEvent` | `type`, `ts`, `durationMs`, `meta` (for paste: `inEditor`, `chars`) |
| `integritySummary` | `attemptId`, `tier`, `counts`, `candidateNote` |
| `reviewAudit` | `attemptId`, `reviewerId`, `action`, `before`, `after`, `ts` |
| `question` (seed) | `slot`, `poolId`, `subSkills[]`, `version` |

### 8. API changes

| Endpoint | Purpose |
| --- | --- |
| `GET /api/assessment/attempts/:id/state` | Restore session and remaining time |
| `PUT /api/assessment/attempts/:id/autosave` | Versioned autosave; 409 on conflict |
| `POST /api/assessment/attempts/:id/submit` | Idempotent submit |
| `POST /api/assessment/attempts/:id/integrity-note` | Candidate note |
| `GET /api/recruiter/assessments/queue?domain=&tier=&status=` | Filtered reviewer queue |

### 9. Success metrics

| Metric | Target |
| --- | --- |
| Attempts with lost answers | Below 0.5% |
| Runner security incidents | 0 |
| Completion rate (started to submitted) | At least 85% |
| Reviewer time per flagged attempt | Down 30% from baseline |
| Accommodation usage without drop-off | No higher drop-off than standard users |
| Seed validation failures reaching production | 0 |

### 10. Rollout plan

1. Ship sandbox runner and server timer behind `ASSESSMENT_V2_1_ENABLED`, internal users only.
2. Run both runners in shadow mode on a sample and compare results.
3. Roll out to 10%, 50%, then 100% of attempts, watching error and completion metrics.
4. Keep the V1 and V2 flags as rollback.

### 11. Risks and mitigations

| Risk | Mitigation |
| --- | --- |
| Sandbox adds latency or cost | Warm container pool; limit concurrency; measure p95 early |
| Partial credit changes existing score distributions | Run old and new scoring side by side and review the differences before switching |
| Integrity tiers perceived as accusations | Reviewer-only visibility, neutral wording, candidate note, human decision required |
| Pool randomization creates unfair difficulty differences | Pools only contain items with the same difficulty and sub-skill; monitor item analytics |

### 12. Open questions

- Which sandbox technology fits the hosting environment (self-managed Docker, a hosted service, or serverless isolates)?
- What retention period should apply to code submissions and integrity events?
- Should Practice mode use the same pools as Secure mode?
- Who owns reviewer SLAs and escalation?

## Part 3: Prompt for a Coding Agent

Paste the following into Cursor, Claude Code or a similar tool, from the repository root.

```text
You are working in the SARATHI repository (React + TypeScript + Vite frontend, Node/Express backend). I want you to implement "Skill Assessment V2.1" on top of the existing V2 assessment system. Work in small, reviewable steps and do not break existing V2 behavior.

## Existing structure (do not restructure)
- Frontend components: src/components/assessment/ (AssessmentV2Shell, ModeSelect, RulesConsent, ActiveAssessmentEngine, QuizPanel, CodeWorkbench, TestOutputConsole, ProjectTask, QuestionPalette, ResultsReport, SkillGapPlan, CameraCheck, IntegrityBanner). Every file must stay under 200 lines.
- Hooks: src/hooks/ (useAssessmentEngine, useCountdown, useAutosave, useIntegrityMonitor).
- Question seeds: server/src/data/seeds/assessment/*.json.
- Backend: server/src/services/assessmentV2/ (gradingService, integrityService, reviewService) and server/src/services/runner/ (runnerDriver, localDevDriver, sqlDriver).
- Flags: VITE_ASSESSMENT_V2 (client) and ASSESSMENT_V2_ENABLED (server). Add ASSESSMENT_V2_1_ENABLED on both sides; V2.1 behavior must be off when it is false.

## Phase 1 (do this first, then stop and summarize)
1. Sandboxed runner
   - Define a RunnerDriver interface: run({ language, code, tests, limits }) -> { passed, failed, stdout, stderr, timedOut }.
   - Replace the child-process JS execution with an isolated sandbox (prefer isolated-vm or a Docker-based runner behind an adapter; pick the one that works with our current setup and explain the choice). Limits: no network, memory 128MB, CPU/time limit configurable, output size cap.
   - Add a Python driver using the same interface.
   - Harden sqlDriver: single SELECT/WITH statement only; reject PRAGMA, ATTACH, DDL, DML, multiple statements; 1000-row cap; timeout.
   - Ensure hidden test inputs and expected outputs are never returned to the client; return only aggregate counts.
2. Server-authoritative timer and resume
   - Store startedAt, deadlineAt (include accommodation multiplier), and saveVersion on the attempt.
   - Add GET /api/assessment/attempts/:id/state and make PUT autosave versioned (409 on conflict). Make submit idempotent and reject submissions after deadlineAt + 10s grace (grade the last autosave instead).
   - Update useCountdown to take remaining time from the server and re-sync on resume.
   - Update useAutosave to queue failed saves in sessionStorage, retry with exponential backoff, and expose a status: saved | saving | offline. Show it in the ActiveAssessmentEngine top bar.
3. Tooling
   - Add `npm run validate:seeds` (unique ids, valid type, difficulty 1-3, >=2 hidden tests per code question) and run it in CI.
   - Add an ESLint max-lines (200) rule for src/components/assessment/.
   - Add unit tests for gradingService (40/60 weighting, evidence caps, practice-mode cap) and the SQL validator; add an end-to-end test for start -> refresh -> resume -> submit.

## Phase 2 (only after I confirm Phase 1)
4. Scoring: partial credit with weightedPassRate = (visiblePassed*1 + hiddenPassed*2) / (visibleTotal*1 + hiddenTotal*2) times difficulty points; move weights and evidence-cap thresholds to server/src/config/assessmentScoring.json per domain with current values as defaults. Keep a flag to compare old vs new scoring side by side.
5. Question pools: add slot/poolId/subSkills/version to seeds, select per attempt avoiding previously seen items.
6. Integrity: paste events record inEditor and char count; integrityService computes a reviewer-only Low/Medium/High tier from configurable thresholds; never change the score; add a candidate note endpoint (max 500 chars).
7. Reviewer queue: filters (domain, tier, status), sorting, and an audit log of every decision.
8. Accessibility: 1.0x/1.5x/2.0x time options, high-contrast and larger-text toggles in RulesConsent, keyboard navigation with visible focus, ARIA labels on QuestionPalette and CodeWorkbench, and aria-live announcements for the <5 minute warning.

## Rules
- Do not make any automatic score deductions based on integrity events. Keep all wording non-accusatory.
- Do not send webcam frames anywhere; CameraCheck stays local-only.
- Keep each frontend file under 200 lines; split into new files when needed.
- Prefer additive changes and migrations that are backward compatible with existing attempts.
- Before coding each phase, list the files you will create or change and any assumptions. After coding, list what you tested, what you could not test, and any follow-ups.
- Ask me before choosing between materially different options (for example sandbox technology) if the repo setup does not make it obvious.

## Definition of done for Phase 1
- Candidate code never runs in the API server process.
- Refreshing mid-test restores answers, code, current question and remaining time.
- A dropped network for up to 5 minutes does not lose answers.
- Hidden test data never appears in any network response (verify in the browser network tab and in a test).
- All new tests and validate:seeds pass in CI; with ASSESSMENT_V2_1_ENABLED=false the V2 flow behaves exactly as before.
```

### How to use this

1. Review the PRD and adjust priorities or targets to your timeline.
2. Paste the prompt and let the agent finish Phase 1 before you approve Phase 2.
3. Answer the open questions in the PRD (especially sandbox technology and retention) before implementation, because they affect the design.
